## Executive recommendation

Start with a bounded web-only corrective, make deployment recoverable, then ship
the server corrective before starting balance or content work.
v8.4's authoritative objective state, legal-target presentation, passive
standings/respawn behavior, setup previews, result explanations and responsive
HUD hierarchy are valuable foundations and should remain. The next work should
close four cross-layer contracts that the release tests did not fully exercise:

1. **Idempotent authoritative actions:** one scoped action has at most one
   gameplay effect, and acceptance, completion, rejection, reconnect and rematch
   state must agree.
2. **Supported-input reachability:** touch hit targets and keyboard focus must
   reach every interactive Board, Spend, Training and Results control.
3. **Runtime truth:** production navigation, Operations wave fronts and personal
   REQ must match the behavior promised by their data and UI.
4. **Release recoverability:** a game-server deploy must be able to restore both
   web and server code to an exact previous build.

No weapon, combat, reward-rate, bot-pressure or Director-tier tuning is justified
by this audit. Human fun, comprehension, comfort and retention evidence is still
missing. D2-D4 outcome measurement remains deferred.

## Consolidated findings

### P0 — None confirmed

The audits found no active outage, demonstrated production data loss or reason
for an emergency rollback. Current HTTP, asset, release-endpoint and WebSocket
connectivity checks pass. The findings below are P1 release-certification
blockers and should gate the next applicable release.

### P1 — Release-blocking correctness and recoverability

#### A1. COCS actions lack round-scoped idempotency and round-persistent outcomes — Confirmed

The page builds several card IDs without a stable player identity
(`app/page.tsx`, `issueCocsOrder`, `activateCocsBoardCard`, `spendCocs`). The
server keys `Room.cocsCards` globally by that ID, does not deduplicate an action
before applying it, and retains pending/card state across `Room.start()`.
Accepted order-log entries are also settled as `done` even when the HOLD/ATTACK
task remains active (`server/room.mjs`, `settleCocsCards`). Terminal and buy
outcomes do not have an equivalent complete outcome path, and some early refusal
paths return without an authoritative rejection.

Observed consequences include duplicate BUY charging twice, stale successful
outcomes settling a reused ID, cards surviving a rematch, and optimistic actions
remaining pending. `app/page.tsx:activateCocsBoardCard` compounds this by saying
`ORDER ACCEPTED` immediately after dispatch rather than after authority replies.

**Required invariant:** within a round, a server-derived action identity has at
most one gameplay effect. Duplicate delivery returns the cached outcome; reuse
with a different payload is refused. Status moves monotonically through
`queued -> accepted -> complete|refused|expired`; acceptance never implies
completion.

#### A2. A game-server deploy cannot restore previous server code — Confirmed

`scripts/deploy.sh` backs up and restores only `dist/`, while
`token-arena-server.service` runs `server/game-server.mjs` and shared game source
from the mutable checkout. A failed `--with-game-server` deployment can therefore
restore the old web bundle while restarting the new server source. The deploy
gate checks service activity and web assets, but not a join/start/snapshot flow
or matching server build identity.

**Required invariant:** web and game server promote and roll back as one
identified release. A rollback restores the exact previous commit/artifacts and
passes the same smoke gate as a deployment.

### P1 — Functional and supported-input blockers

#### B1. Touch capture can sit above Board and Training controls — Browser-reproduced

`--z-touch: 6` is above `--z-board: 5` and `--z-panel: 2`; the move and look
zones accept pointer events over broad screen regions (`app/globals.css`). At
844x390 and 390x844, independent hit tests placed Board rows/header actions and
Training actions below touch capture zones. A tap can move/look/jump instead of
activating the visible control.

#### B2. Training completion creates keyboard-only dead ends — Browser-reproduced

When a cursor surface owns input, the page consumes Tab globally
(`app/page.tsx`, global key handler). Training completion does not move focus
from the canvas into its action card, and replacing FINISH TRAINING with KEEP
PLAYING can drop focus. A keyboard-only user can therefore be unable to continue
or leave the course.

#### B3. The shared target model is not navigation-backed in production — Confirmed

`latticeTargetModel()` asks `navigationRoute()` for `map.nav` and `map.edges`,
but the production `getMap()` shape exposes authored navigation through other
fields (including `navNodes`/lattice data). The page supplies no explicit route
context or team-visible supply cuts. With no route resolver, topology-legal
targets default to reachable and geometric distance ranks them. ARRAY endgame
legality also disagrees with authority because the view model first excludes
the archetype from its capturable set.

The coach, strip and board do share one model as intended; the defect is that
their shared production input is incomplete.

#### B4. Personal REQ is not a complete player-facing vertical slice — Confirmed

The live HUD exposes a REQ balance, but the app has no purchase catalogue or
caller for `NetClient.buy`. Fourteen catalogue entries advertise `launch:true`,
while only a subset has concrete simulation effects. Unsupported entries can
debit REQ and occupy buff state without producing the advertised world effect.
Operations Puma is accepted by the co-op simulation but rejected by the room's
generic `item.launch` gate.

The production page also has no caller for `NetClient.command`, and its Board
uses SABOTAGE where the protocol accepts CUT. Displayed controls and wire adapters
must be treated as one vertical slice.

This should be narrowed to a truthful supported set before adding more items.

#### B5. Operations ignores authored per-wave front counts — Confirmed contract gap

`directorWavePlan()` publishes per-wave/per-tier fronts, but
`refreshTargets()` uses the tier-wide front count and the emitted wave event
reports that tier value. Periodic retargeting then points the whole living force
at one primary node. This invalidates the authored escalation contract before
any D1-D4 balance conclusion can be drawn.

Runtime contract tests across D1-D4 are allowed here: they verify data wiring,
not win rates or difficulty balance.

#### B6. NEXT MISSION can inherit the previous mission's checkpoint — Confirmed

`startCampaignMission(id)` spreads the current config and sets a new mission but
does not clear/recompute `checkpoint`. Completing one mission from a later
checkpoint can therefore start the next mission after its opening stages.

### P2 — Clarity, accessibility and research quality

#### C1. Results and portrait surfaces need one more reflow pass — Browser-reproduced

At 390x844, the modal footer can be wider than its clipped panel because Results
renders five or more non-wrapping actions. `NextMatchPanel` and the footer also
duplicate replay/loadout actions, weakening the intended single invitation. A
state-dependent portrait top score can extend beyond the viewport.

#### C2. Modal stack, remapping and announcements are incomplete — Confirmed

- Opening Settings over Pause can leave two active modal dialogs without inerting
  the lower one or restoring focus to the opener.
- Command Board, voice, vehicle and spectator prompts retain literal B/V/E-style
  labels or shortcut metadata outside the centralized binding model.
- Continuously changing combat status regions can produce live-region churn,
  while elimination/respawn lacks one concise event announcement.

#### C3. Board and Spend auxiliary controls lack keyboard parity — Browser-reproduced

Board shortcuts cover list movement and current-card activation, but not
PIN/CLOSE/EXPAND or nested actions. Spend shortcuts buy a selected sink but
cannot reach a multi-target select or SKIP through normal focus traversal.

#### C4. Local/network and spectator presentation still have parity gaps — Confirmed

Local order events are not filtered through the same team-visibility rule used
online. Spectator Results can fall back to actor 0 and present another player's
contribution/reward language. Some order totals labelled as team totals are
global match totals.

#### C5. Onboarding competes with the title and is not binding-derived — Confirmed

Fresh storage can mount Onboarding while `entered === false`, covering the title
before the primary entry action. Completion and skip share one unversioned bit,
and introductory control copy remains hard-coded. This is a sequence and
measurement problem; whether the content load overwhelms novices is a human
hypothesis.

#### C6. Training can end before required lessons are available — Known deferred gap

Training remains an ordinary 15-minute match with normal dominance, Director and
HQ-loss conditions. Operations lessons can require waiting for another spend
window. This was explicitly deferred in v8.4, so it is not a newly discovered
release regression. Its frequency and frustration cost require human
observation; the possibility is code-proven. Training reliability is not signed
off until the protected scenario work passes.

#### C7. Support contribution and progression are not yet one policy — Hypothesis

Results explain LATTICE hold, captures, orders and REQ contribution, while XP
and challenges mostly use generic kills/wins/objective time/captures. This can
create incentive drift, but the audit does not prove players notice or change
behavior. Define a contribution ledger first; tune values only after research.

#### C8. The human protocol needs governance and optional local instrumentation — Confirmed process gap

The existing worksheet is a strong formative outline, but it lacks a consent
script, withdrawal/deletion rules, data retention, standardized timing anchors,
facilitator deviation log and artifact manifest. There is no opt-in journey log
linking intended start, training outcome, result action and actual second-match
start. Silent production analytics are not recommended.

### P3 — Quality and documentation debt

- Browser/device evidence is ephemeral; there is no tracked Playwright runner,
  trace/screenshot manifest or CI artifact.
- Page-level orchestration is often checked by source regex/no-op callbacks, so
  model correctness can pass while adapters are wrong.
- `/api/version` and deployment verification identify only a release string,
  not commit/build/protocol or a matching web/server pair.
- Server persistence/socket failures and build identity are weakly observable.
- Command Board copy says the cursor key or an arena click returns to combat,
  while the explicit BOARD surface intentionally blocks both. The truthful exits
  are the bound Command key, Escape and CLOSE.
- There is no stable browser performance gate; benchmark duration/reporting and
  swallowed render errors must be corrected before promotion to a gate.
- README/SYSTEMS mode counts and TESTING/browser-language have drifted.
- Lint passes with a large warning baseline; adopt a no-new-warning ratchet
  rather than mixing a repository-wide cleanup into gameplay work.

## Implementation roadmap

### Phase 0 — Corrective program: truthful web first, then safe server change

Do not promote another ordinary `--with-game-server` release as rollback-safe.
The current production service need not be taken down, but the controlled WP0.2
cutover and rollback drill must precede the server-side action redesign.

#### WP0.1 — Web-only truth and campaign fixes — **S**

1. Change immediate Command Board feedback from ACCEPTED to QUEUED; only a
   matching authoritative `cardId` may produce ACCEPTED/COMPLETE/REFUSED.
2. Set campaign checkpoint from action intent and target mission, never from the
   current config: `next-mission` starts with `null`; resume uses
   `checkpointFor(campaign, targetMissionId)`.
3. Make footer/version verification exact enough that HTML with a v8.3 footer
   and unrelated v8.4 text fails.
4. Correct deployment/verification documentation to describe dist-only rollback,
   the ephemeral v8.4 browser smoke and the difference between connectivity and
   deployed-commit proof.

**Acceptance**

- No Board path displays ACCEPTED before a matching authoritative event.
- A stale checkpoint from another mission never carries into NEXT MISSION.
- Resume preserves only a valid checkpoint for the selected target mission.
- Real launch-coordinator tests construct the selected Match at the expected
  opening/checkpoint; no-op callback or source-regex tests are insufficient.
- A stale-footer fixture containing the new version elsewhere is rejected while
  cache-policy and linked-asset verification remain intact.

#### WP0.2 — Identified web/server artifacts and recoverable deployment — **L**

Build once from a clean commit and publish a hashed release manifest containing
web and server artifacts, commit, build ID, release, protocol, runtime/lock
identity and an explicit compatibility declaration. Server-changing releases
promote and roll back the identified pair as one coordinated operation; web-only
releases may retain a declared-compatible server. Store history and progression
outside every release directory and retain the previous manifest/artifacts.

Expose exact structured identity and readiness from both services. Establish
real peer protocol negotiation now: JOIN/CREATE must store and enforce the peer
version rather than merely reporting a mismatch.

**Acceptance**

- Dirty, unidentified or hash-mismatched candidates are rejected.
- Failure injection after each partial cutover restores the previous manifest
  and exact web/server SHAs.
- History and progression survive success, injected failure, SIGTERM and
  rollback; schema changes have a tested backup/migration/rollback path.
- Deployment and rollback pass connect, join, host, start, snapshot and
  clean-leave WebSocket smoke tests.
- Exact web/server build IDs and protocol compatibility are verified; a version
  substring is not identity.
- The stale-tab client compares `buildId`, not only a release label.
- A five-minute soak retains expected build IDs, reports zero tick/socket/
  persistence errors, advances successful history/progression flush times and
  stays below a declared event-loop-lag budget.
- Server cutover either drains/announces active rooms or explicitly states that
  matches terminate; the plan does not imply zero downtime.

#### WP0.3 — Round-scoped idempotent COCS actions and outcomes — **L**

1. Add a dedicated server-issued `roundRevision`, a reconnect-stable authenticated
   seat identity and one monotonically increasing client action sequence shared
   by ORDER, ECONOMY, TERMINAL, COMMAND and BUY. Do not reuse a lobby lifecycle
   counter as the round identity.
2. Authenticate/validate round identity and perform duplicate lookup before rate
   limiting, gating, enqueueing or application. Bind a key to its canonical
   payload: an exact retry returns the cached outcome; the same scoped key with a
   different payload is refused as `id-reuse`.
3. Keep a round-long execution ledger/tombstone independent from the bounded
   presentation cards and events, so 300 later cards cannot erase dedupe state.
4. Author outcomes where the simulation actually applies the action. Use
   simulation ticks (`queuedTick`, `acceptedTick`, `terminalTick`) and one
   immutable state vocabulary: `queued -> accepted -> complete`, or
   `queued|accepted -> refused|expired`.
5. Keep HOLD/ATTACK accepted until the objective completes, expires or is
   replaced. Record terminal channel completion/interruption and immediate
   vault, buy, command and economy outcomes.
6. Emit a correlated reason for every authority-received request with a valid
   action key, including dead/ended/disconnected and sim-side refusal paths.
7. Run `beginRound` only on a real new round/rematch. Same-revision reconnect
   retains server outcomes/rate limits, replaces optimistic client state from the
   current full snapshot and idempotently retries unresolved envelopes.
8. Persist strip transitions from authority instead of deriving them only from a
   bounded transient event window. Apply existing team privacy to outcomes in
   full snapshots, deltas, results and reconnects.

**Protocol decision:** mandatory round/action identity requires protocol v4 or
an explicitly negotiated capability. V4 requires identity on all five action
frames and echoes it in outcomes. A transitional v3 adapter may scope an existing
stable client `cardId` by current round and authenticated seat; a frame without a
usable idempotency key is `upgrade-required`. Never mint a fresh server ID for
each legacy retry or silently execute mixed versions with weaker semantics.

**Acceptance**

- Duplicate ORDER, ECONOMY, TERMINAL, COMMAND and BUY frames have one effect in
  direct Room and real-WebSocket tests.
- Duplicate BUY after more than 300 intervening cards still charges once.
- Same key/different payload, stale/future round and cross-actor reuse are
  refused; same scoped key/payload intentionally returns its cached outcome.
- Two same-team players acting on one tick receive distinct identities.
- HOLD-on-owned-node, task replacement, TTL expiry, round end, terminal
  interruption and immediate one-shot outcomes reach the documented state.
- No UI displays ACCEPTED before its matching authoritative identity.
- 301 unrelated events cannot regress a settled strip state.
- A new round contains no previous cards/cooldowns; same-round reconnect
  preserves running/terminal outcomes and never reapplies a retry.
- Requests never received by authority remain explicitly uncertain rather than
  being falsely described as terminal.
- Two seeded runs produce identical outcome ticks and private fields never leak.

### Phase 1 — Supported inputs and truthful tactical runtime

WP1.1 may run in parallel with Phase 0. No intervening release may claim touch or
keyboard accessibility readiness until its browser and physical-device gates
pass.

#### WP1.1 — Touch hit ownership and keyboard focus scopes — **M**

- Put only actionable Board/Spend/Training bounds above touch capture, or clip/
  suspend move/look zones while those bounds are active.
- Move focus into Training on a completion beat and preserve it across FINISH ->
  KEEP PLAYING.
- Replace blanket Tab suppression with surface-specific focus scopes.
- Include Board header/nested controls and Spend target/SKIP in normal traversal.

**Acceptance**

- At 844x390 and 390x844, `elementsFromPoint()` at the bounding-box centre of
  every visible, enabled Board, Spend and Training target (scrolled into view
  when needed) returns that control or its child.
- Activating those controls does not mutate movement/look/fire/jump state.
- Keyboard-only users can continue, finish and leave Training from canvas focus.
- Every enabled Board/Spend control is reachable with a visible focus ring.
- After FINISH TRAINING, `document.activeElement` is KEEP PLAYING, never body;
  Enter and Space activate it.
- Tab/Shift+Tab remains in the owning surface and neither opens standings nor
  seeds combat input.
- Physical iOS Safari and Android Chrome multi-touch checks pass.

#### WP1.2 — Production navigation and authority parity — **M**

Provide the target model a cached deterministic route context built from the
actual arena/Match navigation shape. Consume team-visible cut state and align
ARRAY/endgame legality with the authority's `capturableBy` rule.

**Acceptance**

- Production-shape local and network tests report `routeSource: 'navigation'`.
- Ground-unreachable HOLD/ATTACK targets are omitted; SCAN retains its authored
  ground-route exemption.
- Team-visible cuts change LINKED/CUT OFF state and ranking but do not change
  capture legality unless authority is deliberately changed too.
- Verb-specific topology legality, including ARRAY before/during endgame, matches
  `capturableBy` with unrelated gates held open.
- Coach, strip and board agree on guidance. If route reachability becomes an
  authoritative legality rule, add the same deterministic route check server-
  side; otherwise do not claim complete server route parity.
- Route work is cached and does not rebuild the graph every React render.

#### WP1.3 — Truthful personal REQ slice — **M–L**

First choose a supported launch set. Hide/unlaunch any item without a complete
effect. Then add one catalogue/purchase surface shared by local and network paths,
including cost, target, eligibility, effect and refusal feedback. Fix the
Operations Puma room gate. Wire displayed command and purchase actions to
`NetClient.command`/`NetClient.buy`, map Board SABOTAGE to protocol CUT, and hide
any control without a complete adapter.

**Acceptance:** every displayed item creates a tested authoritative world-state
change; no-op/rejected purchases preserve REQ; local and online behavior match;
duplicate cards remain idempotent; private wallets/events stay private. Real
page callbacks emit exactly one valid frame and resolve its authoritative outcome.

#### WP1.4 — Execute authored Operations fronts — **M**

Use `directorWavePlan().fronts` for target selection, spawn distribution and the
published wave event. Preserve deterministic per-front actor assignments during
retargets; only redistribute invalid fronts rather than collapsing the whole
force onto one node.

**Acceptance:** every tier/wave pair matches authored front count, emitted data
and actor distribution. This is contract verification, not D2-D4 balance
measurement.

#### WP1.5 — Viewer/team parity — **S–M**

Filter local order intent through the same policy as online, make spectator
results actor-neutral, clear stale rewards at every round start, and publish or
label order totals with their real team/match scope.

#### WP1.6 — Binding-complete controls and truthful cursor copy — **S**

Resolve Command, Voice, Interact and applicable spectator labels plus
`aria-keyshortcuts` through the binding model. Command Board help must advertise
the bound Command key, Escape and CLOSE—not cursor-key/arena-click exits that the
cursor state machine correctly blocks.

**Acceptance**

- With Command=Y, Voice=I, Interact=L and Cursor=O, routing, visible prompts,
  accessible names, Help and `aria-keyshortcuts` agree; no stale B/V/E remains
  unless explicitly reserved as fixed.
- With Board open, an arena click neither fires nor silently relocks. Advertised
  exits close the Board, and closing the last surface allows user-gesture pointer
  reacquisition.
- Hardware pointer-lock testing confirms Escape never double-triggers Pause.

### Phase 2 — Accessible presentation and first-time reliability

#### WP2.1 — Results, portrait header and modal stack — **M**

- Remove duplicate Next Match/footer actions and route all result actions through
  stable action IDs.
- Wrap/stack the footer at narrow widths and constrain all header columns.
- Allow exactly one active modal; inert the lower layer, restore the exact opener
  and define Settings -> Pause -> game Escape behavior.

**Acceptance:** no document/modal/footer horizontal overflow at all required
viewports; all actions remain visible, focusable and at least 44px on coarse
pointers; exactly one `aria-modal=true` dialog is exposed. While Settings is
open, Pause is inert/hidden from the accessibility tree and cannot receive focus;
closing Settings restores OPEN GRAPHICS & SETTINGS exactly, and a second Escape
resumes/closes Pause.

#### WP2.2 — Event-gated assistive announcements — **M**

Convert continuously changing readouts to non-live groups and announce
objective/order/spend/training/death/respawn transitions once through one
prioritized channel.

Validate with NVDA plus Chrome/Firefox and VoiceOver plus Safari; DOM mutation
counts are useful but do not replace assistive-technology listening.

**Acceptance**

- After initial mount, ten seconds of unchanged combat causes no live-region
  churn.
- Objective, order, spend and training transitions announce once.
- Elimination and respawn announce once each, not on every countdown update.
- NVDA and VoiceOver listening remains mandatory; mutation counts alone do not
  pass this gate.

#### WP2.3 — Title-first, versioned onboarding — **S–M**

Open onboarding only after explicit arena entry. Persist skip and completion
separately with a content version, allow reopening from Help, and derive controls
from current bindings.

#### WP2.4 — Completion-safe training scenario — **L**

Promote the previously deferred protected scenario only after WP1.1 and the
action/runtime contracts are fixed. Prevent time/dominance/HQ failure from
ending an active course, stage or guarantee required spend/terminal/route/wave
opportunities, and disclose practice/no-reward status before launch. Completion
should offer Recommended Match, free practice or Loadout.

**Acceptance:** real Match integration reaches every lesson; no prerequisite is
unavailable for more than 30 seconds without a recovery/skip path; reading cannot
cause failure; all completion/skip/exit paths remain reward/history-free.

### Phase 3 — Evidence, progression policy and retention

#### WP3.1 — Governance-complete human protocol — **S**

Amend `reports/playtest-v8.4-template.md` with consent/recording language,
withdrawal/deletion and retention rules, random participant codes, scenario
assignment, timing anchors, facilitator deviations, adverse-event/stop criteria,
finding confidence and an artifact manifest.

#### WP3.2 — Opt-in local study recorder — **M**

Use a versioned, device-local, inspectable and deletable log only after explicit
study consent. Record an ephemeral session ID, monotonic offsets, viewport/input
class and coarse accessibility flags for journey transitions such as onboarding,
match intent/start, training step outcome, authoritative order/spend outcome,
death/respawn, results action and second-match start.

Do **not** collect player UUID/progress token, IP, name, chat, voice, exact keys,
raw input streams or precise world coordinates. Replays/video need separate
consent. A second match is not "voluntary" without the participant's stated
reason.

#### WP3.3 — Contribution/reward policy — **M, evidence-gated**

Define one authoritative contribution ledger shared by Results, XP and
Challenges. Decide which orders, terminals, repairs, cuts and support actions
deserve bounded credit. Do not set or tune reward weights until the human study
shows an actual comprehension or incentive problem.

### Cross-cutting quality gates — delivered with their owning phase

These are not a final cleanup phase. Each gate must exist before the work package
that depends on it can pass.

1. **With WP0.1/WP0.3:** add application-seam tests that invoke launch/action
   coordinators with a real Match and real callbacks. Retain source-regex tests as
   cheap wiring guards, not behavioral proof.
2. **With WP0.2:** expose build identity, protocol compatibility, readiness,
   persistence health, last successful flush, socket errors and event-loop lag;
   add exact deployment/rollback smoke and failure injection.
3. **With WP0.3:** retain existing real-WebSocket privacy/lifecycle coverage and
   add duplicate frames, current-round reconnect, new-round reset, action privacy
   and mixed-version negotiation.
4. **Before WP1.1 acceptance:** track a Playwright runner, browser matrix, traces,
   screenshots and console/network logs for real clicks, keys, touch events,
   focus, hit testing and pointer lock. Every artifact manifest records commit,
   build ID, command, browser/version/flags, viewport, DPR, UI scale, renderer and
   input mode.
5. **Later performance gate:** fix the 2.5-second default versus 20-second report
   mismatch and make render exceptions fail. Then establish separate declared
   budgets for pinned hardware WebGL and software rendering; never transfer a
   budget between them.
6. Ratchet lint by warning fingerprint, not only total: no warning absent from
   the approved 604-warning baseline may be introduced.
7. Reconcile README/SYSTEMS mode counts, TESTING/browser claims and the release
   evidence documents named in WP0.1.
8. Every release records an explicit skip manifest. The current eight approved
   game skips are the D1-D4 sampled outcome sweep, exhaustive combat-mode sweep,
   18k-step deathmatch, platform-bot sweep, browser-only OfflineAudioContext
   render, 10k-step race, all-arena movement-route sweep and all-arena bot-route
   sweep. New or unexpected skips fail the gate; slow/archive sweeps remain
   scheduled or opt-in and are not human balance evidence.

## Required human questions and measures

After Phases 0–2, run the published cohort protocol and separately report map,
difficulty, gear/progression, input and experience. At minimum measure:

- intended first activity, hesitation and effective rules;
- first contact and dead-to-meaningful-action time;
- training instruction, action, completion, stall, recovery and skip;
- ability to buy REQ and explain the effect;
- five-second identification of dominance loss or HQ siege;
- active-front choice and what changed after an order/spend;
- death cause and expected respawn behavior;
- match-end reason, personal contribution and next intended action;
- actual voluntary second-match start plus the stated reason;
- independent ratings for direction, agency, control predictability and desire to
  continue.

Do not tune combat, bot pressure, roster density, rewards or Director tiers from
this code audit. Select one observed failure at a time after the baseline.

## Preserve these foundations

- Authoritative public dominance/wave/HQ state and per-team private visibility.
- One shared coach/strip/board target model; fix its inputs rather than fork it.
- Deterministic fixed-step simulation, seeded randomness and simulation-tick
  timers; no `Math.random` or wall-clock decisions in simulation.
- Passive Tab standings and passive automatic respawn summaries.
- Compact spectator presentation and stable title-demo action.
- Fresh recommended starts, truthful effective-rules previews and separate
  Director versus bot difficulty.
- Reward-free training with explicit acknowledgement and local evidence.
- Pure/idempotent result and reward view models.
- Remapping, captions, palettes, reduced motion, touch and explicit cursor
  ownership.
- The local 0.8–1.4x Command/Spend/Terminal text scale; do not convert it into
  global HUD or 3D scaling.
- Independent touch pointer capture and input-transparent non-actionable HUD
  space; do not raise the entire HUD above the touch layer.
- `game/cursor-mode.mjs` as the sole pointer-lock owner; fix copy and focus rather
  than bypassing explicit surface ownership.
- Existing weapon/class identities and D1 values until human evidence supports a
  specific change; D2-D4 outcome measurement remains deferred.
